“无法上网”的截图通常不能说明启动失败、节点握手失败还是请求没有经过代理。有效反馈要把现象、发生时间与相应日志连起来。本文处理如何采集和整理证据，网络路径排查另见[终端访问检查](/articles/openclash-lan-check/)。

## 三类日志怎样选择

2026-10-04 核对的正式版 0.47.156 日志页有 Plugin Logs、Core Logs 和 Debug Logs 三类视图。

| 日志 | 适合回答的问题 |
| --- | --- |
| 插件日志 | 下载、配置处理、插件启动流程在哪一步失败 |
| 核心日志 | 运行中的连接、规则和协议错误是什么 |
| 调试日志 | 当前固件、依赖、配置、防火墙、路由等环境状态是什么 |

核心视图里的 Debug 日志等级，与第三个调试日志视图不是同一件事。只把等级调成 Debug 不会自动获得整套环境诊断；生成调试日志也不能替代原始故障时刻的核心报错。

## 按一次故障采集

1. 进入“服务 → OpenClash → 运行日志”。先保存已有的启动错误，再开始新的复现。
2. 写下当前插件、内核、固件版本及正在使用的配置代号。保留网络和节点不变。
3. 若故障涉及请求，在核心日志视图选择合适等级，记录时间后重复一次明确的操作。
4. 下载对应日志；需要环境信息时再使用生成调试日志按钮，等本次生成完成后保存。
5. 采集完成后恢复日常日志等级，避免长期保留不必要的详细请求记录。

不要一次同时发起配置切换、订阅更新和多台设备的请求，否则日志很难对应到某个动作。页面显示为空时，先确认日志刷新、核心运行状态及当前视图，不把“没看见日志”当作没有错误。

## 保留时间线，而不只截最后一行

可以使用下面的反馈结构。只填写自己看到的事实，未确认的项目写“未确认”。

| 项目 | 应保留内容 |
| --- | --- |
| 预期 | 哪一台终端的哪个操作应成功 |
| 实际 | 失败信息、是否所有应用都受影响 |
| 触发时刻 | 时间与时区，对应的日志行 |
| 首次错误 | 第一条相关错误及前后上下文 |
| 唯一改动 | 修改前后的值及结果 |
| 环境 | 固件、插件、核心版本和运行模式 |

诊断脚本会输出依赖、内核、GEO、路由、端口等章节。按错误需要挑选相关部分，而不是从大量日志中随意抓取一行。最近运行日志也可能覆盖不到较早的故障，原始采集必须另行保存。

## 分享前逐项检查

0.47.156 的诊断脚本本身提示上传前屏蔽公网 IP、节点和密码。自动处理不能代替人工检查：订阅 URL 参数、节点域名、认证字段、控制密钥、访问目标和设备信息都可能暴露内容。

在副本中统一替换敏感值，例如将同一节点写成“节点 A”，保留相同对象的对应关系。保留协议类型、错误文本、时间和字段名，避免全篇涂黑而失去诊断价值。原始文件放在个人控制的位置，不提交到站点仓库或公开评论。
